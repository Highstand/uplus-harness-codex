# 페이즈 1 — 요구사항 정리

상태: 사람 검수 대기. 이 문서는 구현 또는 게이트 통과를 증명하지 않는다.

## 근거와 적용 순서

- [PRD](../docs/PRD.md): 서비스 목적, 유저 스토리, 화면 기능, 데이터, 제외 범위.
- [AGENTS.md](../AGENTS.md) 1절의 인터뷰 확정 사항과 4절의 R1 필수 규칙: PRD와 충돌하면 우선 적용.
- 화면 주소·상태·이동의 상세 분해는 페이즈 2에서 `docs/screens.md`와 `reference/flow chart.png`를 함께 확인한다.
- 디자인은 `docs/Design.md`, 토큰 값의 유일한 원본은 `docs/tokens.json`이다. 이 페이즈에서는 해당 내용의 상세 검증을 수행하지 않았다.
- `docs/`와 `reference/`는 읽기 전용이며 Make 시안은 배치만 참고하고 코드를 복사하지 않는다.

## 목표와 완료 기준

매달 데이터가 부족하거나 약정이 끝난 고객이 요금제의 속도 제한 여부와 실제 월 지출을 비교하고, 매장 방문 없이 간단한 입력으로 변경 신청 흐름을 체험하는 모바일 웹 서비스를 만든다. 근거: PRD 1절.

**완료 기준:** 문서에 정의된 화면 5개와 화면 이동·입력 검증·저장 없는 신청 완료 시연을 구현하고, 디자인 규칙과 필수 검사를 통과한 뒤 사람이 최종 확인하면 완료한다. 근거: AGENTS.md 1절.

이번 결과는 실제 통신사 접수가 아니다. 입력은 시연 중 메모리에서만 다루며 서버·DB·localStorage·sessionStorage에 저장하지 않는다. 실제 저장과 Supabase 연결은 제외하고 데이터 구조와 이후 연결 지점만 설계한다. 근거: AGENTS.md 1절.

## 화면과 핵심 기능

| 화면 | 필요한 기능 | 출처 |
|---|---|---|
| 요금제 목록 | 단일 선택 필터 4개, 초기 전체 선택, 가상 요금제 4개를 p01→p02→p03→p04 순서로 표시, 빈 결과 안내, 카드 전체를 눌러 상세 이동 | PRD 4-1 |
| 요금제 상세 | 요금 요약, 정가·24개월 할인·매달 내는 돈의 3줄 구성, 24개월 후 금액, 유형별 데이터·속도 안내, 변경 버튼 | PRD 4-2 |
| 변경 전 확인 | 선택 요금제 요약, 이번 달 요금·위약금·유심 안내 3개를 펼친 상태로 표시, 신청하기·다른 요금제 보기 | PRD 4-3 |
| 변경 신청 | 이름·전화번호·동의, 개인정보 안내 바텀시트, 입력 오류 안내, 유효 입력 전 제출 비활성, 제출 중 중복 실행 방지, 취소 시 입력 삭제 | PRD 4-4. 저장 동작은 AGENTS.md에 따라 제외 |
| 신청 완료 | 시연임을 표시한 완료 안내, 시연 번호 1개와 복사, 방금 입력한 1건의 요금제·금액·이름·마스킹 번호·일시, 처음으로 | PRD 4-5, AGENTS.md 1절 |

이동은 목록 → 상세 → 변경 전 확인 → 변경 신청 → 완료 순서다. 상세에서 목록으로 돌아가면 필터를 유지하고, 변경 전 확인에서 뒤로 가면 상세로 이동한다. 신청 취소는 입력을 삭제하고 상세로 이동한다. 완료의 처음으로·브라우저 뒤로 가기는 목록으로 이동하며 신청 화면으로 복귀하거나 제출을 반복하지 않는다. 근거: PRD 3절, 4-5.

휴대폰 번호는 숫자 11자리 입력 시 하이픈을 표시한다. 이름 빈 값과 전화번호 형식 오류는 포커스 이탈 시 안내하고, 이름은 21번째 글자부터 입력을 막는다. 동의 바텀시트를 닫아도 체크 상태는 유지한다. 근거: PRD 4-4.

시연 번호는 PRD의 `SUB-` + 숫자 6자리 형식을 따른다. 복사 시 토스트는 2초 표시한다. PRD의 실제 접수 제목·처리 상태·이용 목적 문구는 실제 접수로 오인시키지 않도록 시연에 맞게 조정해야 한다. 최종 문구는 미정이며, 개인정보 안내는 아래 확정 문구를 사용한다. 근거: PRD 4-4·4-5, AGENTS.md 1절.

> 실습 화면이며 입력한 개인정보는 저장하지 않습니다.

## 데이터와 이후 저장 연결 범위

- `Plan`: PRD 5절의 필드를 기준으로 p01~p04 가상 데이터 4개를 읽기 전용으로 사용한다. 추천은 p03 고정이며 개인별 계산은 없다. 가격·데이터·속도는 PRD 4절 데이터 표를 그대로 기준으로 한다.
- `Subscription`: PRD 5절의 id, application_no, name, phone, plan_id, privacy_agreed, status, created_at 구조를 이후 저장 연결 설계의 근거로 삼는다. 이번 시연에는 필요한 내용을 메모리에서만 구성하며 `received` 등 내부 상태를 쓰더라도 실제 접수로 표시하지 않는다.
- 신청 번호의 영구적인 중복 방지, 실제 저장 성공·실패, 네트워크 오류 복구는 실제 저장이 제외되어 이번에 검증할 수 없다. PRD의 저장 실패 안내는 향후 저장 연결 시 적용할 요구사항으로 남긴다. 오류를 일부러 발생시키는 시연 요구는 미정이다.

근거: PRD 4-4·4-5·5절, AGENTS.md 1절.

## 제외 범위

- 실제 저장, Supabase 연결, 서버·DB·브라우저 저장소에 개인정보 보관, 실제 통신사 신청 접수 — 인터뷰 확정 사항.
- 로그인·본인 인증·결제·관리자 화면 — PRD 6절.
- 이번 달 요금·위약금 계산 — PRD 4-3·6절. 안내 문구만 사용.
- 신청 상태 변경 처리(`processing` / `completed` / `canceled`) — PRD 6절.
- 신청 내역의 목록·검색·나중에 재조회 — PRD 4-5·6절.
- 개인별 추천 계산 — PRD 4절 데이터 설명.

## 미정 또는 후속 페이즈에서 확인할 것

1. 실제 개인정보 보관 기간과 저장 연결 방식: Supabase 연결 시 확정. 현재 범위의 누락 기능이 아니다.
2. 실제 요금·위약금·유심 정책: PRD 4-3에 초안이며 정책 확인 후 확정한다고 명시되어 있다. 실제 정책으로 검증된 내용이라고 주장하지 않는다.
3. 시연 완료 제목·처리 상태 등 세부 문구: 실제 접수로 오인시키지 않는 원칙만 확정되어 있다. 개인정보 비저장 안내는 확정 문구를 사용한다.
4. 유효하지 않은 요금제 주소, 메모리 없이 완료 주소에 진입하거나 새로고침할 때의 상세 처리는 이 PRD에 없다. 페이즈 2에서 screens와 흐름도를 확인하고, 여전히 없으면 미정으로 보고한다.
5. AGENTS.md에 명시된 줄높이·굵기·일부 크기 토큰 누락은 페이즈 3에서 확인·보고하고 멈춘다. 임의 값이나 다른 종류의 토큰으로 대신하지 않으며 원본은 사용자가 보완한다.

## 사람 검수 요청

목표·필수 규칙 9개·제외 범위·완료 기준을 검수한다. 승인 전에는 페이즈 1 통과로 기록하거나 다음 페이즈를 실행하지 않는다. 현재 구현·브라우저 동작은 검증하지 않았다.
