# M6 — Supabase 저장·조회 연결

## 범위와 상태

- 사용자 요청에 따라 M1~M5 재실행 없이 M6 추가 작업으로 수행.
- SQL 실행과 `.env.local` 설정은 사용자가 완료했다고 알림.
- 구현 및 기존 구현 게이트 통과. 사람 최종 화면 확인은 대기.
- docs/, reference/, 기존 게이트 구현 및 work/progress.json 변경 없음.
- 환경변수 파일 변경 없음, `.env.local`은 Git 제외 확인.

## 구현

- lib/subscriptions.ts: 공개 키의 apikey 헤더로 Supabase REST POST·GET. 별도 패키지/인증/요청 식별 헤더 없음.
- POST는 id/name/phone/plan_id/privacy_agreed/status만 전송. 번호와 생성 시각은 DB 기본값 사용.
- lib/demo.ts: 번호를 직접 생성하지 않고 저장 성공한 UUID만 화면 간 메모리에 전달.
- 완료 화면은 id 조건으로 DB에서 1건을 별도 조회. 로딩·오류·조회 재시도 구현.
- 저장 실패 시 입력과 동일 UUID 유지. 응답 유실 뒤 23505 발생 시 그 UUID의 저장 결과 확인. UPDATE/UPSERT 없음.
- 완료 뒤로가기는 목록으로 이동. 종료·새로고침 시 메모리 id가 없어 화면은 빈 상태가 되지만 DB 행은 남음.
- 개인정보 비저장 안내를 가상 데이터의 실습 DB 저장 안내로 교체. 실제 통신사 접수와 구분.
- 보관 안내는 응답 전 잠정 기본값인 실습 종료 후 수동 삭제 예정. 자동 삭제 구현 없음.

## 검사 근거

- 환경변수 존재 확인 및 subscriptions의 id 조회 limit=0: HTTP 200. 키 값 출력 없음.
- node checks/implementation.mjs: 주소·토큰·금지 문구 검사, webpack 빌드, 린트 모두 성공(errors=[]).
- git diff --check 통과.
- 실제 Chrome, 390×844에서 실행:
  1. 첫 POST 네트워크 실패 후 이름·전화번호·동의 유지.
  2. 다음 POST는 실제 HTTP 201 저장 후 응답 유실을 재현.
  3. 재시도 시 동일 UUID로 기존 행 확인, 중복 행 생성 없음.
  4. 완료 화면 GET 실패 뒤 '완료 정보 다시 확인'은 GET만 수행.
  5. DB 번호1개, 휴대폰 가운데4자리 마스킹, received의 접수 완료(실습) 표시.
  6. localStorage/sessionStorage 모두 비어 있음.
  7. 브라우저 뒤로 목록 이동, 추가 INSERT 없음.
  8. 완료 직접 진입은 빈 상태. 해당 UUID의 DB 행은 유지됨.
- 첫 실행은 개발 모드 effect의 재실행 때문에 GET 오류 재현이 불안정해 검사 스크립트를 수정한 뒤 재실행. 앱 결함으로 기록하지 않음.

## 남은 가상 검증 데이터

가상 이름 M6가상검증, 가상 전화번호01000000000으로 총2건 저장됨. 각 시나리오에서 동일 UUID 재시도는 행을 추가하지 않음.

| 신청 번호 | id |
|---|---|
| SUB-000000 | c8f38b0f-93f4-4341-8ea4-fb2d1b59deeb |
| SUB-000002 | 2a87a342-b45a-4ed0-9a8f-857897ca94b2 |

DELETE 권한을 추가하거나 우회해 삭제하지 않았다. 필요 시 사용자가 Table Editor에서 해당 가상 행을 삭제할 수 있다. 실패한 INSERT도 sequence를 소비하므로 번호 사이의 빈 값은 정상이다.

## 한계 및 최종 확인

- 사용자 요청의 수업용 RLS: anon SELECT 전체 허용. 화면 id 필터는 접근제어가 아니며 실제 개인정보 입력용이 아님.
- 이번에는 원격 스키마/정책을 수정하지 않았고 UPDATE/DELETE 권한의 실제 거절 테스트는 수행하지 않았다.
- 브라우저 호환성 전체 검증 및 CDN 장애 검증은 수행하지 않았다.
- 실제 화면의 저장·조회·실습 안내를 사용자가 최종 확인해야 한다. GitHub 업로드는 이번 작업에서 수행하지 않는다.
